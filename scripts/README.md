# Скрипти

Усі запускаються з кореня проєкту як модулі, з активованим venv і заповненим `.env`:

```bash
python -m scripts.<назва>
```

## Правило, яке варто знати до першого запуску

Скрипти поділені на три види за тим, що вони роблять із даними. Перед запуском
подивись, до якого належить твій.

|                                     | Що робить                                                    | Як позначено                          |
| ----------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------ |
| 🟢**читає**              | нічого не змінює, запускати будь-коли | без прапорців                        |
| 🟡**пише у Firestore**   | потрібен явний`--apply`                               | без нього — пробний прогін |
| 🔴**пише в SchoolToday** | бойова база школи, відкату немає          | окреме підтвердження          |

Скрипти, що пишуть, **за замовчуванням нічого не пишуть**. Спершу показують
повний список змін, і лише з `--apply` виконують їх.

## Дані: SchoolToday і Firestore

### 🟢 `test_schooltoday_connection.py`

Швидка перевірка, що ключ працює: кастомні поля, зведення по базі, за потреби —
одна картка учня.

```bash
python -m scripts.test_schooltoday_connection            # довідники + зведення
python -m scripts.test_schooltoday_connection 930        # + картка учня
python -m scripts.test_schooltoday_connection 930 --raw  # без маскування ПД
```

### 🟢 `test_schooltoday_client.py`

Перевірка клієнта `core/schooltoday.py`: будує payload з вигаданого документа,
проганяє сім перевірок (злиття `customData`, відсутність `pupilIDs`, лікування
телефонів) і робить кілька живих GET-запитів.

Запускати після будь-якої зміни в клієнті або коли школа перейменувала поля.

### 🟢 `audit_firestore.py`

Стан колекції `Svitlo` — скільки документів, які поля, чи перетинаються з базою
ШС по пошті. Корисно перед міграцією.

### 🟡 `backfill_firestore.py`

Перенесення активних учнів зі ШС у Firestore. Зливає два джерела: картку ШС і
старий експорт `DBs/firestore_export_crmstage.csv` (Telegram ID, доступи, ролі
`itt`/`boss`, яких у ШС немає). З'єднує їх по пошті.

```bash
python -m scripts.backfill_firestore --from-snapshot   # з останнього знімка, без запитів до ШС
python -m scripts.backfill_firestore                   # зі свіжими даними, зберігає знімок
python -m scripts.backfill_firestore --apply
```

Повторний запуск безпечний: учні, для яких документ уже створено, пропускаються
за `stPupilId`. Службові й тестові картки виключені списком `SKIP_ST_IDS`.

### 🟢 `verify_backfill.py`

Звірка кожного документа Firestore проти обох джерел, поле за полем.

```bash
python -m scripts.verify_backfill
python -m scripts.verify_backfill --verbose
```

**Важливо:** після чистки даних цей скрипт показуватиме розбіжності зі ШС — і це
очікувано. Ми навмисно виправили ПІБ у Firestore, а в ШС вони лишились старими.

## Якість даних

### 🟢 `audit_data_quality.py`

Регулярна перевірка стану: регістр, пробіли, порядок ПІБ, пошти, телефони.

```bash
python -m scripts.audit_data_quality
python -m scripts.audit_data_quality --show 40
```

Вивід поділений на **дефекти** (потребують дії) і **прийняте** (відомий
погоджений стан — латиничні ПІБ батьків, порожні поля після прибирання по
батькові). Якщо в дефектах з'явилась нова категорія — це або справжня проблема,
або її треба свідомо додати в `ACCEPTED` з поясненням.

Порядок полів у ПІБ батьків звіряється з прізвищем дитини: збіг транслітерацій
підтверджує правильність автоматично.

### 🟡 `fix_data_quality.py`

Чистка: регістр, пробіли, апострофи, кириличні гомогліфи в латинських іменах,
перестановка переплутаних ПІБ батьків.

```bash
python -m scripts.fix_data_quality           # показати всі зміни
python -m scripts.fix_data_quality --apply
```

**Це не просто скрипт, а журнал рішень.** Таблиця `MANUAL` містить 78 випадків,
розібраних поіменно, з поясненням чому саме так: де поля переставлені, де
рідкісне ім'я тільки виглядає прізвищем, де замість прізвища стоїть по батькові.
Коли через півроку хтось спитає, чому в цієї мами порожнє ім'я — відповідь тут.

Скрипт збіжний: повторний запуск нічого не змінить, бо всі правила вже
застосовані. Пошти з помилками доменів **не чіпає** — це логін, і правка може
відрізати людину від акаунта; вони виводяться списком для куратора.

## Синхронізація з SchoolToday

Напрямок один: **Firestore → ШС**. Зворотного немає свідомо — без нього не буває
конфліктів, а отже й тихих затирань. Це означає, що правити дані треба у
Firestore; правка в інтерфейсі ШС буде відкочена наступним синком.

### 🔴 `sync_to_schooltoday.py`

Переносить у ШС усе, що змінилось у Firestore — зокрема й ручні правки, зроблені
в Rowy.

```bash
python -m scripts.sync_to_schooltoday            # показати, що зміниться
python -m scripts.sync_to_schooltoday --apply
```

Не чіпає: `personalFileNumber`, `contractNumber`, `discount`, `isPayer`,
`hideInDiary`, `isHidden` (деактивація лишається ручною), `email`, кастомні поля
«Ролі» та «House» — їх веде школа. Доступ батькам не видає.

Після кожного успішного запису фіксує стан у колекції `SyncState` — це baseline
для drift-репорту.

### 🟢 `drift_report.py`

Показує, де ШС розійшовся з Firestore, **до того як синк це затре**.

```bash
python -m scripts.drift_report
```

Порівнює три стани: що в ШС зараз, що ми туди записали минулого разу
(`SyncState`), і що у Firestore. Без третьої точки напрямок правки обчислити
неможливо — у ШС немає позначки часу оновлення.

Вивід поділений на чотири розділи:

| Розділ                                              | Що означає                                                                                                   |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **Поправили руками в ШС**         | хтось змінив картку в інтерфейсі — синк це відкотить                      |
| **Конфлікти**                              | змінили з обох боків, потрібне рішення людини                                   |
| **Наші зміни, ще не запушені** | поїдуть наступним синком                                                                        |
| **Свідомо не переносимо**        | у Firestore порожньо, у ШС є значення — постійна різниця за побудовою |

Плюс окремо — дублікати в `customData` на боці ШС: `PATCH` не прибирає повторні
записи з тим самим іменем, хоча документація обіцяє повну заміну масиву.

Запускати перед кожним `sync_to_schooltoday --apply`.

## Вікове переведення

Напрямок один: у Firestore ставимо старшу групу тим, кому виповнилось 14, —
далі це саме доїде в ШС наявним синком (`ageGroup` → `classID`). Окремої
інтеграції зі SchoolToday під це немає.

### 🟡🔴 `promote_by_age.py`

Переводить усіх зарахованих учнів молодшої групи (`ageGroup == "younger"`,
`stage == "student"`), кому вже виповнилось 14, у старшу групу: міняє
`ageGroup` на `"older"`, надсилає їм повідомлення в бот з кнопкою переходу в
чат старшої групи і — якщо не вимкнути `--no-sync` — одразу проганяє
`sync_to_schooltoday --apply` та `drift_report`.

```bash
python -m scripts.promote_by_age                    # прев'ю: кого зачепить
python -m scripts.promote_by_age --apply            # перевести + синк ШС + сповістити
python -m scripts.promote_by_age --apply --no-notify
python -m scripts.promote_by_age --apply --no-sync
python -m scripts.promote_by_age --limit 5 --apply
```

Запускати **вручну раз на семестр, перед Induction Week**. Крона немає свідомо:
семестр короткий, подія рідкісна, а список кандидатів треба звірити очима
(окремо показуються ті, у кого немає дати народження, і ті, кому вже > 18).

Збіжний: кандидати відбираються за `ageGroup == "younger"`, тож після `--apply`
вони випадають з вибірки — повторний прогін нікого не переведе і не сповістить
удруге. Історія переведень лягає в колекцію `AgeGroupTransfers`.

Те саме доступне кнопкою в Solar Panel (розділ «Синхронізація зі SchoolToday»,
лише для owner) — щоб не лізти в консоль.

Нагадування, що час переводити, приходить в `ADMIN_GROUP_ID` разом із
дайджестом заявок (`/tasks/admin_review_digest`, кожні 12 год), коли в
молодшій групі зʼявляються учні з 14+.

## Комунікація

### 🔴 `broadcast.py`

Розсилка групі учнів за фільтрами профілю (хаус, вікова група, стадія, ролі).

```bash
python -m scripts.broadcast --house Caledonia --text "Привіт!"        # тільки показати виборку
python -m scripts.broadcast --house Caledonia --text "Привіт!" --yes  # відправити
```

Завжди спершу без `--yes`: побачиш, кого саме зачепить фільтр.

### 🔴 `send_message.py`

Одне повідомлення конкретному Telegram ID. Для ручних випадків — тестерам, після
бага.

```bash
python -m scripts.send_message 123456789 "Текст"
python -m scripts.send_message 123456789 "Текст" -b "Перейти|https://t.me/svitloschool"
```

## Порядок для міграції

Якщо робиш перенесення з нуля:

1. `test_schooltoday_connection` — переконатись, що ключ живий
2. `audit_firestore` — подивитись, що вже є в колекції
3. `backfill_firestore --from-snapshot` — пробний прогін
4. `backfill_firestore --apply` — записати
5. `verify_backfill` — звірити з джерелами
6. `audit_data_quality` — побачити дефекти
7. `fix_data_quality --apply` — почистити
8. `audit_data_quality` — переконатись, що дефектів не лишилось

Знімки бази ШС складаються в `work materials/st_backup/` при кожному запуску
бекфілу без `--from-snapshot`. Вони містять персональні дані — не викладати
нікуди за межі машини.
